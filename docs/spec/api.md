# api ドメイン仕様（事前設計 / 実装保留）

対象モジュール: 将来 `modules/apim.bicep` + `modules/aca-env.bicep` 拡張を想定

## 1. 位置づけ

- 本ドメインは、**Dify の API 経路保護**を目的とする。
- 現時点では未実装（保留）とし、先に API インターフェースを定義する。
- 実装時は APIM をフロントに置き、OAuth 2.0 で保護する。

## 2. To-Be 経路（将来）

`Client -> APIM -> (Private) ACA api`

- インターネット公開 API は APIM のみ。
- Dify `api` コンテナへの直接到達は禁止。
- APIM で認証・認可・レート制御・監査ログを集中管理する。

## 3. インターフェース設計方針（先行定義）

### 3.1 認証/認可
- OAuth 2.0（Bearer Token）を必須化。
- APIM 側でトークン検証（issuer/audience/scope）を実施。
- 未認証は `401`、権限不足は `403` を返却する。

### 3.2 API バージョニング
- パスベース versioning を採用（例: `/v1/...`）。
- 破壊的変更は新バージョンを追加し、旧版は段階廃止する。

### 3.3 共通レスポンス規約
- 正常系: HTTP 2xx + JSON
- 異常系: HTTP 4xx/5xx + 共通エラー形式
  - `code`（機械判定用）
  - `message`（人間可読）
  - `traceId`（追跡用）

### 3.4 最低限の運用ポリシー
- レート制限（例: per-client）
- タイムアウト/リトライ方針
- 監査ログ（呼び出し主体、時間、結果コード）

## 4. 実装保留の範囲

- APIM リソース作成（Bicep）
- OAuth 2.0 連携設定（IdP/アプリ登録/ポリシー）
- API 定義の APIM import（OpenAPI）

> 上記は保留だが、インターフェース契約（URI/認証/エラー仕様）は先行して確定させる。

## 5. 受け入れ基準（設計段階）

- API 経路保護方針が `APIM + OAuth 2.0` で合意されている。
- 主要 API の URI 命名・バージョニング方針が文書化されている。
- 認証エラー/業務エラーの返却規約が定義されている。
- 実装着手時に参照できる未実装タスク（保留事項）が明示されている。
